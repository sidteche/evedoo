- **MSRC ingest is opt-in and never redistributed (P21-N5)**
  - Decision: Build MSRC CVRF ingestion in cve-db-builder behind an explicit --enable-msrc flag, off by default, printing the Microsoft APIs Terms of Use notice on first use. Where MSRC has a verdict for a (CVE, product) pair it overrides the NVD/CPE match; absence of an MSRC row falls back to NVD rather than suppressing the finding.
  - Rationale: Microsoft APIs Terms of Use section 3(b)(14) flatly prohibits redistributing data obtained via the API, and 3(b)(4) permits building a database only "as necessary to enable an intended usage scenario for your Application". A locally-synced offline scanner cache is squarely an intended usage scenario, and the sync-only architecture satisfies 3(b)(14) by construction. Applicability is genuinely ambiguous: section 1(d) enumerates the governed APIs and MSRC CVRF is not among them, while section 1(b)'s broad definition arguably sweeps it in, and no MSRC-specific accompanying terms could be located. The general Microsoft website ToU is more restrictive still, saying personal and non-commercial use. Making acceptance an affirmative act via an opt-in flag rather than a side effect of running a sync is the defensible position if the tool is ever sold. Technically verified as sound: MSRC gives an exact FixedBuild and KB per CVE, and every MSRC CPE product string resolves in the existing NVD dictionary after lowercasing, so ProductID to CPE to matcher identity is a real bridge.
  - Cost if wrong: If the terms are later read as prohibiting even local caching for commercial users, the feature must be disabled — but because it is opt-in and ships no data, no distributed artifact would need recall and no user would be in breach without having affirmatively enabled it. If MSRC coverage proves thinner than NVD for some product, the fallback rule means findings are never lost, only left at NVD precision.
